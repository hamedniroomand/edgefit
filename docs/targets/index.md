# How results are computed

Every result edgefit gives comes from data that is vendored in the package, pinned to a version, and listed with its source and license. This page explains the layers. The per-target pages cover the details.

## Targets

| Target         | Runtime                                                                  | Export conditions                 |
| -------------- | ------------------------------------------------------------------------ | --------------------------------- |
| `workerd`      | [Cloudflare Workers Node.js compatibility](/targets/workerd)             | `workerd`, `worker`, `browser`    |
| `bun`          | [Bun Node.js compatibility](/targets/bun)                                | `bun`, `node`                     |
| `deno`         | [Deno and Deno Deploy Node.js compatibility](/targets/deno)              | `deno`, `node`                    |
| `deno-deploy`  | [Deno Deploy Node.js compatibility](/targets/deno#deno-deploy)           | `deno`, `node`                    |
| `netlify-edge` | [Netlify Edge Functions compatibility](/targets/netlify-edge)            | `node`                            |
| `vercel-edge`  | [Vercel Edge runtime compatibility](/targets/vercel-edge) (experimental) | `edge-light`, `module`, `browser` |

Run `edgefit targets` to print this list along with the exact data versions:

```
workerd  Cloudflare Workers
  conditions workerd, worker, browser
  data workers-nodejs-compat-matrix@ee58120 (workerd 1.20260929.1), curated overrides from https://github.com/cloudflare/workerd/tree/v1.20260929.1/src/node, Web APIs from runtime-compat-data@b964f92 (npm 0.0.5), DOM globals from dom-globals (typescript 5.9.3)
```

## The layers

<Steps>

### Module resolution

The graph is resolved with esbuild, using the target's export conditions before the standard ones such as `import` and `default`. This matters: many packages ship a separate build per runtime, and a package's Workers build can be free of the Node APIs its Node build uses.

### The Node compatibility matrix

[workers-nodejs-compat-matrix](https://github.com/cloudflare/workers-nodejs-compat-matrix) records, for every export of every Node built-in, whether it exists on workerd, Bun and Deno, compared with a Node baseline. It is generated by loading each module inside each runtime. This is the base answer for every Node API.

### Curated overrides

The matrix only knows whether something exists. It cannot tell that `fs.watch` on Workers exists and throws, or that `async_hooks.createHook` on Bun returns a hook that is never called. Each target has an override file, read by hand from the runtime's source at the same version, that marks these as `unsupported` or `mocked`. An API that throws only for some options is marked `mismatch`, and the entry can name those options, so only a call that passes one of them is a finding. Every entry links to the file it was read from, and that link is the `see` line in your report.

### Web API data

Globals such as `caches`, `FileReader` and `navigator.gpu` are checked against [runtime-compat-data](https://www.npmjs.com/package/runtime-compat-data) 0.0.5 (CC0-1.0). It only fills in what the matrix does not describe, and its findings get their own `web` category at warning level because the data is generated automatically.

### DOM globals

A window has about 640 globals that a worker scope does not. Examples are `DOMParser`, `Node`, `HTMLElement` and `XMLSerializer`. A server runtime has few of them, and a read of a missing one by its plain name throws a `ReferenceError`. The list is `data/dom-globals.json`. It holds the names that `lib.dom.d.ts` of TypeScript 5.9.3 declares as a `var`, `let`, `const`, `function` or `class`, and `lib.webworker.d.ts` does not. A runtime can also have some of these names, such as `alert` on Bun and Deno and `localStorage` on Deno. A name that the runtime has is not missing on it.

Each runtime has its own column of the names that it has:

- The workerd, Bun and Deno columns come from `typeof globalThis[name]` on the versions that the data pins: workerd 1.20260929.1, Bun 1.4.2 and Deno 2.9.7. Deno Deploy uses the Deno column.
- The Netlify column is the list of these names in the production witness of a Netlify Edge Function. Deno 2.3.1 has the same names, except `window`.
- Vercel Edge has no column, so no name is present there. No name is in the middleware names of the Vercel witness or in `@edge-runtime/vm` 5.0.0.

The web API data and the overrides win for a name that they also describe. A finding for one of these names is reported only when the code reads the plain name as the module loads, see [Browser globals by their bare name](/guide/findings#browser-globals-by-their-bare-name). The list ends at TypeScript 5.9.3, so a global that a later release adds is not in it, see [Limitations](/guide/limitations#the-data-has-an-age).

### Target settings

Last, each target applies its own settings: the compatibility date and flags on workerd, the pinned version on Bun, the import map on Deno and Netlify.

Vercel Edge has no matrix dump to start from, so its Node data is the baseline cut down to what Vercel's documentation allows. See [Vercel Edge](/targets/vercel-edge).

</Steps>

## Why the data is pinned

Results only change when your project or the data changes. That makes edgefit safe to put in CI: a build does not go red on its own because a data source was updated overnight, and a regression report compares like with like.

The cost is that data can lag behind runtime releases. A scheduled workflow in the repository probes the latest runtimes and flags overrides that have gone stale, so the data can be bumped in a release. See [Compatibility data](/contributing/data).
